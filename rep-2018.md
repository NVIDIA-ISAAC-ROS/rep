We propose introducing the concept of a tensor as a natively supported type in ROS 2 Lyrical Luth.

Below is a sketch of how this would work for initial feedback before we write a proper REP for review.


# Abstract

Tensors are a fundamental data structure often used to represent multi-modal information for deep neural networks (DNNs) at the core of policy-driven robots. We introduce `rcl::tensor` as a native type in `rcl` as a container for memory that can be optionally externally managed. This type would be supported through all client libraries (`rclcpp`, `rclpy`, ...) the ROS IDL `rosidl`, and all RMW implementations. The default implementation of `rcl::tensor` operations for creation/destruction and manipulation will be available on all supported platforms. With the presence of an optional package and some environment configuration, a platform-optimized implementation for `rcl::tensor` operations can then be swapped in at runtime to take advantage of accelerator-managed memory/compute. Through adoption of `rcl::tensor` in developer code and ROS messages, we can enable seamless platform-specific acceleration determined at runtime without any recompilation or deployment.

* Tensor, as a native type, can be used in ROS messages and their payloads can optionally be stored in externally managed memory.
* Operations with tensors through standard interfaces can be optionally implemented with accelerated libraries determined at runtime.


# Motivation

ROS 2 should be accelerator-aware but accelerator-agnostic like other popular frameworks like PyTorch or NumPy. This enables platform-specific optimizations when possible but still remaining compatible as necessary.

## Background
AI robots and policy-driven physical agents rely on accelerated deep neural network (DNN) model inference through tensors. Tensors are a fundamental data structure to represent multi-dimensional data from scalar (rank 0), vectors (rank 1), and matrices (rank 2) to batches of multi-channel matrices (rank 4). These can be used to encode all data flowing through such graphs including images, text, joint positions, poses, trajectories, IMU readings, and more.

ROS messages, however, expect their payloads to reside in main memory with field types such as `int8[]` or multi-dimensional arrays. This requires these payloads to be copied from main memory to accelerator memory and then copied back to main memory after blazingly fast processing in order to populate a new ROS message to publish. Type adaptation in `rclcpp` provides a solution for this, but it requires all participating packages to have accelerator-specific dependencies and only applies within the client library, so RMW implementations cannot apply optimized for accelerator memory, for example.

Additionally, without a canonical tensor type in ROS 2, a patchwork of incompatible tensor libraries is arising across various ROS packages which causes impedence mismatches with popular deep learning frameworks such as PyTorch and others.

## Target User Flows
1. ROS node A uses `rcl::tensor` to encode their joint positions and ROS node B expects `rcl::tensor` for joint positions. ROS package B has a dependency on accelerator-XYZ tensor package and ROS node B submits work to a accelerator-XYZ. When receiving a `rcl::tensor` additionally queries the `rcl::tensor` if it is GPU-backed.
1. ROS package developer uses `rcl::tensor`-based APIs to create, encode, and process images into tensors. On a Raspberry Pi, this uses all CPU/main memory processing as usual, but on a platform with a GPU with an environment variable set and a GPU-specific ROS package available, all of the memory handling and tensor operations are run through a GPU-accelerated library instead. The RMW implementation queries the `rcl::tensor` when serializing to determine that is in fact backed by a known GPU-accelerated library, so it encodes the wire format differently to optimize its transport.




# Requirements

* Provide a native way to represent tensors across all interfaces from client libraries through RMW implementations.
* Make available a set of common operations on tensors that can be used by all interfaces.
* Enable accelerated implementations of common tensor operations when available at runtime.
* Enable accelerator memory management backing these tensors when availale at runtime.
* Optimize flow of tensors for deep neural network (DNN) model inference to avoid unnecessary memory copies.
* Allow for backwards compatibility with all non-accelerated platforms.


# Definition

```

struct rcl::Tensor
{
    std::vector<size_t> shape; // shape of the tensor
    std::vector<size_t> strides; // strides of the tensor
    void* data; // pointer to the data
    size_t size; // size of the data
    size_t itemsize; // size of the data type
    size_t ndim; // number of dimensions
    size_t nbytes; // size of the data in bytes
    size_t nitems; // number of items in the data
}
```
